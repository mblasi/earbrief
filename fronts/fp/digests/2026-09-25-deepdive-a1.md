I want to start with a question that sounds trivial but contains a hidden revolution. When you write a function, what is it actually for? Most engineers will say it's for computing something — given some inputs, produce an output. That's true, but it's incomplete. The deeper truth is that a function is a contract. And the signature of that function — the type information about what goes in and what comes out — is the written form of that contract. And once you learn to read contracts, everything changes about how you design systems.

Here's why this matters, especially for someone building or reasoning about complex systems like machine learning pipelines or agent orchestration. The difference between a function whose type tells you what it does and a function whose type tells you almost nothing is the difference between code you can confidently combine and code that will surprise you at runtime. This is not academic. It's the difference between a codebase that breaks when you refactor and one where the compiler tells you the safe moves before you even test.

Let me ground this with a concrete example, because the idea becomes real only when you see it applied.

Imagine you're building a feature engineering pipeline for a machine learning model. You have some raw data, and you need to transform it. In most imperative code, you might write a function that looks like this: takes in some data, mutates it in place, returns nothing explicitly — or worse, returns the mutated data and also has side effects you have to remember. But there's a cleaner path. You write a function with a signature that says: I take a data frame of type A, and I return a data frame of type B. That's not just documentation. That's a constraint. If the types A and B are different — maybe A has raw features and B has normalized features — then you now have a promise that gets checked at compile time. Any code that feeds the output of this function somewhere expecting raw features will fail before you run it. You've turned a class of runtime bugs into a refactoring error that the compiler catches.

This is the first level of what types are really doing: they're making your assumptions explicit and mechanically verifiable. But there's a deeper layer.

The second insight is about composition. Functions with clear signatures are composable. Let me illustrate that with the same pipeline. Once you have a function that takes raw data and produces normalized data, and another function that takes normalized data and produces feature vectors, and a third that takes feature vectors and produces predictions, you can chain them together. The signature of each function describes exactly how it fits to the next. The output type of the normalizer is the input type of the feature extractor. The compiler can verify that they fit together before you ever run the code. This is function composition at the type level, and it's profound because it means you can build complex systems out of small, verified pieces.

But here's the thing that really changes your thinking: composition is not just about piping data through functions. It's about building larger functions from smaller ones. If you have a function that normalizes data and a function that extracts features, you can build a single function that does both, and its signature is just the composition of the two: raw data in, features out. That composed function has the same property of clarity and composability as the originals. You can keep composing, building larger and larger functions, and at every level the types keep you honest.

Now I need to address the question every engineer asks at this point: isn't this restrictive? Don't you lose flexibility when everything has to match types?

The answer is counterintuitive. The constraint is not restrictive, it's clarifying. When you sit down to design a piece of code and you have to decide on the types — what goes in, what comes out — you're forced to think clearly about what that code is supposed to do. You can't be vague. You can't have a function that might take a string or an integer or a list and might return any of those or none. You have to commit to a contract. And that commitment forces you to think in a way that most engineers only do for their most critical code. It's like writing a formal specification, except the specification is the code itself. They're the same thing.

And here's the payoff I want you to carry out of this: once your code is typed, refactoring becomes safe. In dynamic languages, refactoring is scary. You change something and you hope you caught all the places it's used. In a typed system, you change the type of a function and the compiler tells you every place that breaks. Not at runtime — at compile time. You get a checklist of everything that needs to change. And you can be confident that once the compiler is happy, you haven't missed anything. You can refactor aggressively because you have guarantees.

Let's go deeper into composition because it's where the real power emerges.

Function composition is just the mathematical idea that if you have a function from A to B, and a function from B to C, you can build a function from A to C by running them in sequence. The intermediate type B vanishes — it becomes an implementation detail. All that matters at the interface is that you started with A and ended with C. This is trivial mathematics. It's also the key to building systems that scale in complexity without scaling in incomprehensibility.

In practice, this looks like having small functions that each do one clear thing, each with a simple type signature. And then building larger functions by composing them. A function that loads data. A function that validates it. A function that transforms it. A function that stores it. Each one has a signature that says exactly what it accepts and what it produces. And you can combine them in any order that makes sense type-wise — if the output of one doesn't match the input of the next, the compiler says no before you deploy.

But there's a psychological shift that happens when you really internalize this. You start thinking about functions not as subroutines that do stuff, but as transformations. A function is a thing that turns one type into another type. That perspective changes how you decompose a problem. Instead of thinking about a series of steps you're going to execute, you think about a series of type transformations. And once you're thinking in type transformations, composition becomes the obvious way to structure code. You're not gluing pieces together. You're building a pipeline where the output type of each stage matches the input type of the next.

I want to point out something subtle here that matters a lot for people building machine learning systems. In the modern ML world, data shape is almost as important as the data itself. A feature vector that's supposed to be five hundred dimensions is useless if it's actually three thousand. A label tensor that should be batch size times ten is broken if it's batch size times a hundred. These are exactly the kinds of errors that types catch. And they're errors that can be devastating in production because they can silently propagate through your pipeline, corrupting downstream outputs in ways that are hard to debug.

When you commit to clear types in your ML pipeline — the shape of raw data, the shape of normalized features, the shape of the labels — you turn shape mismatches into compile-time errors. Or, in languages that aren't compiled in the traditional sense, you turn them into errors that happen at the entry point of your code, not buried deep in matrix multiplication.

Now let me address the relationship between types and testing, because this is where the idea really becomes economically interesting.

In dynamically typed systems, testing is the primary tool for catching bugs. You have to write tests for all the paths through your code because the language can't verify that your types are compatible. You test the happy path, the sad path, the edge cases. It's a lot of work, and it's fundamentally incomplete — you can never test every possibility.

In typed systems, types catch whole categories of bugs automatically. You don't need to test that a function that's supposed to take an integer doesn't accidentally get a string, because the type system prevents it. You don't need to test that the output of function A can be passed to function B, because the compiler verifies it. This means your tests can focus on the actual logic, on the semantic behavior, not on type mismatches. Your test suite becomes smaller and more focused. And that's not just efficiency — it's a sign that the code is actually clearer.

Let me summarize the shape of the idea so you can carry it forward.

A function is not just a computation. It's a contract, and the type signature is the contract in written form. That signature says: I will accept this type and produce this type, and no other. The clarity of that contract matters because it lets you reason about larger systems. When you combine functions through composition, the types of the functions have to match — output of one equals input of the next. That matching is not a limitation. It's a guarantee. The type system becomes a mechanical proof that your larger system is correctly connected.

And here's the insight that changes how you design: you can design a large system by specifying nothing but the types. What are the inputs? What are the outputs? What are the intermediate representations? Once you've written down those types, the actual implementation often becomes obvious, sometimes trivial. The hard part is getting the types right, because the types are the specification. Get the types right and the code almost writes itself.

This is especially powerful in machine learning contexts where the shape and interpretation of data matter intensely. Commit to types for your data shapes, your transformations, your models. And then build your system by composing functions that respect those types. The result is a system where shape mismatches and architectural errors are caught early, and refactoring is safe.

The practical path forward is to start small. Pick a part of your system where the logic is clear and the types are easy to specify. Write functions with explicit types. Compose them. Feel the difference when the compiler tells you that you've made a mistake in how you connected things, before you run anything. Most of you are probably not going to immediately switch to a purely typed language. But you can apply this thinking to the parts of your code that matter most. And the ones you'll apply it to first are the ones where bugs are most expensive — data pipelines, model interfaces, the boundaries between systems.
