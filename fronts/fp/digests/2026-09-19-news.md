## 1. Agents as Composed Pure Functions: The Elm Architecture Pattern Scales

The Elm Architecture—decoupling state, logic, and side effects—has become the de facto pattern for building reliable agents. Unlike imperative agent frameworks that interleave mutation and action, the functional pattern treats an agent as:

```
Agent = (State, Message) → (NewState, Effects)
```

**Why this matters:**

- **Deterministic replay:** Agent decisions are pure functions of state + input. Given identical state and messages, the agent always produces identical outputs. Critical for debugging, testing, and red-teaming.
- **Compositional effects:** Each agent can declare *which* side effects it performs (API calls, memory writes, tool invocations) without executing them. This decouples logic from execution, enabling safe simulation and sandboxing.
- **Type safety:** Elm's type system prevents entire classes of agent bugs: missing tool handlers, invalid state transitions, malformed outputs.

**Recent validation:** David Nolen's work on ClojureScript agents shows that immutable message passing (core.async, CSP patterns) scales to complex orchestration without locks or explicit concurrency control. The pattern is now adopted by major labs for multi-agent systems.

## 2. Algebraic Data Types (ADTs) for Tool Schemas and Agent Protocols

Type-driven development is reshaping how agents define tool use. Instead of JSON schemas, frontier labs now use **sum types** (ADTs) to express the space of agent actions:

```clojure
(deftype AgentAction
  (ApiCall [endpoint params auth])
  (MemoryWrite [key value timestamp])
  (Escalate [reason]))
```

**Benefits:**

- **Exhaustiveness checking:** Compiler ensures agent handles all possible action types.
- **Invalid states are unrepresentable:** An agent can't attempt an API call without credentials because the type system forbids it.
- **Tool composition:** Combine tools algebraically (e.g., "ApiCall that requires auth" + "MemoryWrite that logs to audit trail" = new tool).

**Practical example:** Simon Peyton Jones' recent work on Haskell type-level programming shows how to encode neural network shapes as types, catching dimension mismatches at compile time rather than runtime. Applied to agents: encode "this tool requires prior context lookup" as a type constraint. Agent code that violates this fails *before* running.

## 3. Immutable Logs for Agent Memory: Event Sourcing as Constraint

The functional approach to agent memory replaces imperative state mutation with **immutable append-only logs**. Each agent decision is recorded as an event; state is reconstructed by replaying the log.

**Advantages:**

- **Auditability:** Every agent action is logged with timestamp, decision context, and outcome.
- **Reversibility:** Incorrect agent decisions can be undone by removing the offending event(s) and replaying.
- **Multi-agent coordination:** Agents synchronize state by exchanging logs, not shared memory.

**Real deployment:** Meta's Brain2Qwerty (brain-computer interfaces) uses event sourcing for agent-like assistants that track user intent over long conversations. Each intent is an immutable event; agent state is deterministically reconstructed.

**Curriculum implication:** Learn CQRS (Command Query Responsibility Segregation) and event stores (EventStoreDB, Kafka). Understand how Clojure's durable data structures (persistent vectors/maps) enable efficient event replay. This is the operational foundation for production agents.

## 4. Type-Safe LLM Output Parsing with Parser Combinators

Parsing LLM outputs is notoriously fragile. Functional programming offers a composable alternative: **parser combinators**—small, reusable parsers built from pure functions.

```haskell
parseAction = parseApiCall <|> parseMemoryWrite <|> parseEscalate
parseApiCall = string "API_CALL" *> spaces *> parseEndpoint
```

**Compositionality:** Each parser is a pure function; combine them with operators like `<|>` (choice) and `*>` (sequence). The result is:

- **Readable:** Code structure mirrors grammar structure.
- **Composable:** Reuse parsers across projects.
- **Type-checked:** Haskell parser combinator libraries verify parse result types at compile time.

**Live libraries:** Bartosz Milewski's recent talks cover Parsec (Haskell) and Nom (Rust). Both enable LLMs to produce validated, structured outputs that integrate seamlessly with agent logic.

## 5. Declarative Data Pipelines for Training + Inference

Functional data engineering (Polars, Scala's Spark, Clojure's Specter) treats pipelines as compositions of pure transformations:

```clojure
(-> dataset
    (filter #(> (:confidence %) 0.9))
    (map #(update % :tokens tokenize))
    (group-by :model-version)
    (reduce aggregate-metrics))
```

**Why for agents:** Agent training requires pipelines that:

- **Are deterministic:** Same input always produces same output (enables reproducibility).
- **Are inspectable:** Each stage produces intermediate data for debugging.
- **Are composable:** Reuse sub-pipelines across experiment variants.

**Functional reactive programming (FRP):** Libraries like RxPy (reactive extensions) enable agents to express logic as event streams: "whenever tool execution completes, update memory and emit next action." This scales to multi-agent choreography without explicit control flow.

## 6. Domain-Driven Design for Agent Boundaries

**Ubiquitous Language:** Functional DDD uses types to encode domain concepts. For agents:

```haskell
newtype UserId = UserId Int
newtype ToolRequest = ToolRequest String
newtype AgentDecision = AgentDecision Action

executeAgentAction :: AgentDecision → IO AgentOutcome
```

Each domain entity (user, tool, decision) is a distinct type. This prevents accidental mixing (e.g., passing a UserId where ToolRequest is expected).

**Aggregate roots:** Agent state is an aggregate—a cluster of entities with strong consistency guarantees. The functional approach ensures aggregates remain consistent by treating all updates as pure transformations that can be validated *before* commit.

**Curriculum focus:** Read Eric Evans' DDD book, then study how functional languages encode bounded contexts using module systems. Understand how immutability enforces aggregate boundaries. Apply this to multi-agent systems: each agent is an aggregate; interactions are events exchanged between aggregates.

## 7. Testing Agents with Property-Based Testing

Functional testing uses **property-based testing** (Hypothesis in Python, QuickCheck in Haskell, Proptest in Rust): define invariants that should hold *for all possible inputs*, then let the framework generate randomized tests.

Example agent invariant:

```haskell
prop_agent_never_loses_context =
  forAll (arbitrary :: Gen AgentState) $ \state →
  forAll (arbitrary :: Gen [Message]) $ \messages →
    let (state', _) = foldM stepAgent state messages
    in (memory state') `containsAll` (memory state)
```

**For agent testing:**

- **Coverage:** QuickCheck generates adversarial inputs (edge cases, race conditions, malformed tool responses).
- **Repeatability:** Failed tests include the minimal input that triggers the failure, enabling fast debugging.
- **Regression prevention:** Properties become living documentation. New features either satisfy properties or fail visibly.

**Advanced:** Shrinking—when a property fails on a complex input, the framework automatically simplifies it to the smallest failing case. For agents, this catches subtle state management bugs that manual tests miss.

## Summary: The Functional Agent Stack

Building production agents via functional programming yields:

1. **Pure logic** (state machines, algebraic data types) decoupled from **side effects** (API calls, memory mutations). This enables safe simulation and testing.

2. **Immutable event logs** replace imperative state, enabling auditability, reversibility, and multi-agent coordination.

3. **Type systems** encode domain constraints, preventing entire categories of runtime errors.

4. **Composable transformations** (parsers, data pipelines, reactive streams) reduce code duplication and enable rapid iteration.

5. **Property-based testing** catches edge cases that manual tests miss, ensuring robustness at scale.

The path for FP practitioners entering agentic systems: master **pure state machines** (Elm, ClojureScript), then layer in **event sourcing** (logs, causality), then add **type-driven protocol design** (GADTs, dependent types), then scale via **reactive orchestration** and **property-based verification**.

Unlike imperative agent frameworks that hide complexity in imperative loops, functional approaches make the full contract explicit: *these are the states, these are the transitions, these are the effects, and these invariants always hold.*
