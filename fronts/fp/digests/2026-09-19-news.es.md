## 1. Agents como Funciones Puras Compuestas: El Patrón de Arquitectura Elm Escala

La Elm Architecture—desacoplamiento de estado, lógica y side effects—se convirtió en el patrón de facto para construir agents confiables. A diferencia de frameworks imperativos que intercalan mutación y acción, el patrón funcional trata un agent como:

```
Agent = (State, Message) → (NewState, Effects)
```

**Por qué importa:**

- **Replay determinístico:** Las decisiones del agent son funciones puras de estado + input. Dado estado y mensajes idénticos, el agent siempre produce outputs idénticos. Crítico para debugging, testing y red-teaming.
- **Efectos composicionales:** Cada agent puede declarar *qué* side effects ejecuta (llamadas API, escrituras de memoria, invocación de herramientas) sin ejecutarlos. Desacopla lógica de ejecución, habilitando simulación y sandboxing seguros.
- **Type safety:** El sistema de tipos de Elm previene clases enteras de bugs de agents: handlers de herramientas faltantes, transiciones de estado inválidas, outputs malformados.

**Validación reciente:** El trabajo de David Nolen en ClojureScript agents muestra que message passing inmutable (core.async, patrones CSP) escala a orquestación compleja sin locks o control explícito de concurrencia. El patrón ahora es adoptado por laboratorios mayores para sistemas multi-agent.

## 2. Algebraic Data Types (ADTs) para Esquemas de Herramientas y Protocolos de Agentes

El desarrollo type-driven está remodelando cómo agents definen tool use. En lugar de esquemas JSON, laboratorios frontera ahora usan **sum types** (ADTs) para expresar el espacio de acciones de agent:

```clojure
(deftype AgentAction
  (ApiCall [endpoint params auth])
  (MemoryWrite [key value timestamp])
  (Escalate [reason]))
```

**Beneficios:**

- **Exhaustiveness checking:** Compilador asegura agent maneja todos tipos de acción posibles.
- **Estados inválidos son no representables:** Un agent no puede intentar API call sin credenciales porque el sistema de tipos lo forbidea.
- **Composición de herramientas:** Combina herramientas algebraicamente (ej., "ApiCall que requiere auth" + "MemoryWrite que registra a audit trail" = herramienta nueva).

**Ejemplo práctico:** El trabajo reciente de Simon Peyton Jones en programación a nivel de tipos Haskell muestra cómo codificar formas de redes neuronales como tipos, atrapando desajustes de dimensión en compile time en lugar de runtime. Aplicado a agents: codifica "esta herramienta requiere lookup previo de contexto" como constraint de tipo. Código de agent que viola esto falla *antes* de ejecutar.

## 3. Logs Inmutables para Memoria de Agent: Event Sourcing como Constraint

El enfoque funcional a memoria de agent reemplaza mutación de estado imperativa con **logs append-only inmutables**. Cada decisión de agent se registra como evento; estado se reconstruye reproduciendo el log.

**Ventajas:**

- **Auditabilidad:** Cada acción de agent se registra con timestamp, contexto de decisión, outcome.
- **Reversibilidad:** Las decisiones incorrectas de agent pueden deshacerse removiendo los eventos ofensivos y reproduciendo.
- **Coordinación multi-agent:** Agents sincronizan estado intercambiando logs, no memoria compartida.

**Deployment real:** Brain2Qwerty de Meta (brain-computer interfaces) usa event sourcing para assistants tipo agent que rastrean intención del usuario sobre conversaciones largas. Cada intención es evento inmutable; estado del agent se reconstruye determinísticamente.

**Implicación de curriculum:** Aprende CQRS (Command Query Responsibility Segregation) y event stores (EventStoreDB, Kafka). Entiende cómo las estructuras de datos durables de Clojure (persistent vectors/maps) habilitan replay de eventos eficiente. Esta es la base operacional para agents en producción.

## 4. LLM Output Parsing Type-Safe con Parser Combinators

Parsear outputs de LLM es notoriamente frágil. La programación funcional ofrece alternativa composicional: **parser combinators**—parsers pequeños, reutilizables construidos de funciones puras.

```haskell
parseAction = parseApiCall <|> parseMemoryWrite <|> parseEscalate
parseApiCall = string "API_CALL" *> spaces *> parseEndpoint
```

**Composicionalidad:** Cada parser es función pura; combínalos con operadores como `<|>` (choice) y `*>` (sequence). El resultado es:

- **Legible:** Estructura de código espeja estructura de gramática.
- **Composable:** Reutiliza parsers entre proyectos.
- **Type-checked:** Bibliotecas de parser combinator Haskell verifican tipos de resultado parse en compile time.

**Bibliotecas live:** Las charlas recientes de Bartosz Milewski cubren Parsec (Haskell) y Nom (Rust). Ambos habilitan LLMs producir outputs validados, estructurados que se integran sin fricción con lógica de agent.

## 5. Data Pipelines Declarativos para Training + Inference

La ingeniería de datos funcional (Polars, Spark de Scala, Specter de Clojure) trata pipelines como composiciones de transformaciones puras:

```clojure
(-> dataset
    (filter #(> (:confidence %) 0.9))
    (map #(update % :tokens tokenize))
    (group-by :model-version)
    (reduce aggregate-metrics))
```

**Por qué para agents:** El entrenamiento de agentes requiere pipelines que:

- **Sean determinísticos:** Mismo input siempre produce mismo output (habilita reproducibilidad).
- **Sean inspeccionables:** Cada etapa produce datos intermedios para debugging.
- **Sean componibles:** Reutiliza sub-pipelines entre variantes de experimento.

**Functional reactive programming (FRP):** Bibliotecas como RxPy (reactive extensions) habilitan agents expresar lógica como event streams: "cuando tool execution completa, actualiza memoria y emite siguiente acción." Escala a coreografía multi-agent sin control flow explícito.

## 6. Domain-Driven Design para Límites de Agent

**Ubiquitous Language:** DDD funcional usa tipos para codificar conceptos de dominio. Para agents:

```haskell
newtype UserId = UserId Int
newtype ToolRequest = ToolRequest String
newtype AgentDecision = AgentDecision Action

executeAgentAction :: AgentDecision → IO AgentOutcome
```

Cada entidad de dominio (usuario, herramienta, decisión) es tipo distinto. Esto previene mezcla accidental (ej., pasar UserId donde ToolRequest es esperado).

**Aggregate roots:** El estado del agent es un aggregate—cluster de entidades con garantías de consistent fuerte. El enfoque funcional asegura agregados permanezcan consistentes tratando todas updates como transformaciones puras que pueden ser validadas *antes* de commit.

**Enfoque de curriculum:** Lee libro DDD de Eric Evans, luego estudia cómo lenguajes funcionales codifican bounded contexts usando sistemas de módulos. Entiende cómo inmutabilidad refuerza límites de aggregate. Aplica a sistemas multi-agent: cada agent es aggregate; interacciones son eventos intercambiados entre aggregates.

## 7. Testing Agents con Property-Based Testing

El testing funcional usa **property-based testing** (Hypothesis en Python, QuickCheck en Haskell, Proptest en Rust): define invariantes que deben mantener *para todos inputs posibles*, luego deja que el framework genere tests aleatorizados.

Ejemplo de invariante de agent:

```haskell
prop_agent_never_loses_context =
  forAll (arbitrary :: Gen AgentState) $ \state →
  forAll (arbitrary :: Gen [Message]) $ \messages →
    let (state', _) = foldM stepAgent state messages
    in (memory state') `containsAll` (memory state)
```

**Para testing de agents:**

- **Cobertura:** QuickCheck genera inputs adversariales (edge cases, race conditions, tool responses malformadas).
- **Repeatabilidad:** Tests fallidos incluyen el input mínimo que dispara el fallo, habilitando debugging rápido.
- **Prevención de regresión:** Las propiedades devienen documentación viva. Nuevas features satisfacen propiedades o fallan visiblemente.

**Avanzado:** Shrinking—cuando propiedad falla en input complejo, el framework lo simplifica automáticamente al caso fallido más pequeño. Para agents, esto atrapa bugs sutiles de gestión de estado que tests manuales pierden.

## Resumen: El Stack Funcional de Agentes

Construir agents en producción via programación funcional rinde:

1. **Lógica pura** (máquinas de estado, algebraic data types) desacoplada de **side effects** (llamadas API, mutaciones de memoria). Habilita simulación y testing seguro.

2. **Logs de eventos inmutables** reemplazan estado imperativo, habilitando auditabilidad, reversibilidad, coordinación multi-agent.

3. **Sistemas de tipos** codifican constraints de dominio, previniendo categorías enteras de errores runtime.

4. **Transformaciones componibles** (parsers, data pipelines, reactive streams) reducen duplicación de código e habilitan iteración rápida.

5. **Property-based testing** atrapa edge cases que tests manuales pierden, asegurando robustez a escala.

El path para practicantes de FP entrando en sistemas agenticos: domina **máquinas de estado puras** (Elm, ClojureScript), luego capa **event sourcing** (logs, causalidad), luego agrega **protocol design type-driven** (GADTs, dependent types), luego escala via **orquestación reactiva** y **verificación property-based**.

A diferencia de frameworks imperativos de agents que ocultan complejidad en loops imperativos, enfoques funcionales hacen el contrato completo explícito: *estos son los estados, estas son las transiciones, estos son los efectos, e estos invariantes siempre se mantienen.*
