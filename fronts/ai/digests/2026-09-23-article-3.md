Brian Houck from DX asks the question that precedes all others: what was code review actually solving before AI arrived?

The numbers are sobering. At Meta, lines of code per human diff jumped one hundred six percent year over year. Diffs per developer per month rose fifty-one percent. Eighty percent of that came from agentic AI. Meanwhile, diffs reviewed within twenty-four hours are declining. In some large groups, reviewers face thousands of pending reviews.

The math is broken. Developers want to spend about seven percent of their time on review. AI is generating enough code that it would require ten times that. You can't ask humans to move faster. So the question becomes: what do we lose if we automate review away?

Here's what Brian found: developers identified defect detection as the primary reason for code review. But defect-related comments made up only fourteen percent of actual review comments. In practice, code review serves many other purposes. More than half of developers use reviews to explore alternative solutions. Many pointed to knowledge transfer and gaining awareness of what teammates are building.

The visible output of code review is better code. The invisible output is a better engineering organization.

This is the distinction Brian is pushing against the tech world to understand. Code review is how teams build shared understanding of a system. It's how junior developers learn from experienced ones. It's how architectural intent gets surfaced, questioned, and refined. It's how one engineer's mental model becomes the team's mental model.

Organizations don't become resilient because one person understands a subsystem. They become resilient because many people do.

So when Meta's RADAR system lands three hundred thirty thousand diffs with a third of the revert rate and one-fiftieth the production incidents, that's operationally stunning. But what does it mean for the engineers who didn't see those diffs? What did they not learn? What mental models didn't get shared? What questions never got asked because the code auto-merged while people were in meetings?

Brian isn't anti-automation. He's pro-deliberation. The solution isn't to ask humans to review faster. It's to ask: which changes actually deserve human attention? Which ones need human judgment, not just verification? Which ones need to be seen because they teach something?

He calls this the difference between code review as a gate and code review as a forum. Gating is about safety. Forum is about learning. AI can gate effectively. But it can't replace the forum.

The uncomfortable truth is that many organizations have been ignoring good code review practices for years. Keep changes small. Write meaningful descriptions. Run automated checks before asking humans. Review frequently, in bounded sessions. Select reviewers who know the code.

Research from two thousand sixteen showed that timely feedback, review size, and understanding the motivation for change were the top three challenges. That research was a decade old before AI arrived. The problems weren't new. They were just ignored at scale.

AI didn't create this crisis. It inherited it and amplified it.

So Brian's argument is surgical: before asking AI to fix code review, ask whether your team built the habits that make code review effective in the first place. Small changes. Protected reviewer time. Automated routine checks so humans focus on judgment.

Once those fundamentals are in place, AI has a role. The developers DX interviewed don't want review to disappear. They want AI to remove the parts that don't require human judgment so human attention can go where it matters. Catch security issues. Flag high-risk changes. Surface impact. Handle routine. Let humans do judgment.

The RADAR model walks that line. Low-risk changes auto-merge. High-risk changes go to humans. A stratified system instead of a binary gate.

But the question remains: as automation expands, what gets lost? The RADAR team acknowledges this explicitly. Automated review improves efficiency. But it could suffer knowledge transfer. That's a tradeoff worth monitoring.

Brian's final move is the most important. Don't ask "does it work?" Ask "how does it maximize the time and value of human judgment?" That's the metric that matters when AI enters the review process.
