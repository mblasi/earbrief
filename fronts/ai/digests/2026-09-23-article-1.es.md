Rachel Laycock, CTO en Thoughtworks, escribió algo herético el dos de septiembre: tal vez code review no es el problema. Tal vez code review es cómo hemos estado resolviendo el problema incorrecto todo el tiempo.

El trigger fue un panel con Brian Houck de DX en Code Remix. Brian argumentó que IA está produciendo más código que humanos pueden revisar. En Meta, líneas de código por human diff aumentaron ciento seis por ciento en un año. Pull request sizes crecieron sesenta y cuatro por ciento. Su preocupación: vamos a automatizar code review y perder knowledge transfer, mentoring junior, y ownership colectiva. La respuesta de Rachel: por qué estamos esperando hasta code review para hacer esas cosas?

Esto es una crítica quirúrgica de cómo equipos de software realmente trabajan en 2026. Por dos décadas, el pull request se convirtió en el centro de todo. Escribe código, terminalo, empaquetalo, tirálo sobre la pared, luego ten la conversación importante acerca de si era la cosa correcta en la forma correcta. Rachel odia esto. Ha perdido demasiadas horas a merge conflicts argumentando acerca del modelo de governance mismo.

Su principio es antiguo y sólido: acorta feedback loops. Si feedback es valioso, no lo remuevas. Muévelo más temprano. Así que si quieres explorar soluciones alternativas, hazlo antes de implementar una. Si quieres knowledge transfer, pair program. Si quieres que ingenieros junior aprendan cómo ingenieros experimentados piensan, déjalos trabajar con ingenieros experimentados mientras están pensando, no después cuando todo está hecho y cristalizado en un diff.

El argumento se extiende a ownership colectiva. No relies en pull requests para decirle a la gente qué alguien más ya construyó. Organiza equipos para construir y operar software colectivamente. Usa pairing, mob programming, design sessions en whiteboards. Estos crean ownership más temprano, antes de que el código exista.

Para alineación arquitectónica, diseña junto y encode los constraints importantes como fitness functions. Para formatting, linting, seguridad: automatiza. No deberíamos estar argumentando acerca de whitespace en 2026.

La implicación radical: code review by exception, no by default. Hay cambios que absolutamente garantizan otro humano mirando. Cambios arquitectónicos fundamentales. Cualquier cosa cruzando boundaries de seguridad. Cambios con huge blast radius. Cualquier cosa el equipo dice que no están seguros. Pero no cada línea. No porque agents van a revisar más rápido, sino porque esperar hasta code review para tener conversaciones importantes es architecturally backwards.

La preocupación de Rachel acerca del argumento de Brian es sharp. Él habla de equipos acumulando cognitive debt: el software crece mientras los humanos entendiéndolo shrink. Ella está de acuerdo que esto es real. Solo no piensa que mandatory pull requests lo defiendan. Si agents producen substantially más implementación, equipos necesitan ser deliberados acerca de mantener entendimiento a través de collaborative design, pairing, good boundaries, executable architecture, shared operational responsibility.

El framing al final es perfecto: necesitamos que ingenieros entiendan sistemas, no diffs.

Code review fue un workaround. Funcionó cuando humanos solo podían producir código a cierta velocidad. Ese constraint se fue. Así que la pregunta no es cómo revisar código más rápido. La pregunta es por qué estamos esperando hasta code review para tener todas las conversaciones importantes. Pairing temprano resuelve más problemas. Design sessions resuelven más problemas. Shared responsibility resuelve más problemas. Code review, heredado como ceremony, los resolvía todos de una vez pero mal.

La explosión de IA no está rompiendo code review. Está exponiendo que code review era la herramienta incorrecta todo el tiempo.
