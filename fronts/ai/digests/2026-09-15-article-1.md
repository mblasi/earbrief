Addy Osmani recently published a frame for using agents in old codebases that directly contradicts the "greenfield illusion" most teams enter with. The idea is simple: throw an agent at a decade-old monolith and it will produce code that compiles and passes the tests, but with the wrong system design and brittle tests, because the agent has no way to know which constraints live outside the repository. The code itself is no longer a complete description of how the system actually behaves.

Brownfield codebases accumulate institutional knowledge. One team's micrositе has excellent test coverage because it was built two years ago. Another team's auth flow has three implicit invariants that nobody documents because everyone who understands them sits on that team. Commerce sites that look like a single experience to users often hide five microsites with different quality standards, different testing practices, different owners. The invisible constraints aren't bugs. They're often features: the business runs on that ugly behavior, and an agent will happily "fix" it behind a green test suite.

Osmani proposes a zoning system: green zones are safe, well-tested, using modern conventions and good isolation. Yellow zones are mixed quality—agents can work there but need characterization tests written first. Red zones contain auth, billing, permissions, payroll—sensitive enough that the only safe agent mode is human pairing on every step or no changes at all. The zones aren't metaphorical. Three rules make them operational. A person draws the map, not the agent, because agents naturally gravitate toward the scariest file (it has the most interesting names). Zones only move when earned: yellow becomes green once characterization tests exist and the module owner has reviewed the agent's first changes. And zones set the verbs: green is a tight loop, yellow is tests first, red is human on every step.

The next principle is equally important: write down what the code can't say. Agents are actually good at inferring system structure from the codebase itself. What you want to give them is the stuff that is not obvious from reading the code. Business nuance. Trade-offs that explain why the system is structured a certain way. Patterns and conventions that aren't enforced by static analysis. Domain-specific rules. External constraints. Historical context behind counter-intuitive implementations. Everything else—most markdown documentation sprawl—is noise in the context window and wastes tokens.

For yellow and red work, Osmani recommends a separate research pass that produces a short comprehension memo: entry points, owners, callers, existing abstractions, tests, production signals, relevant history, open questions. Claims should cite a file, issue, ownership record, or dashboard. The default loop otherwise wastes its archaeology. The agent works out how the auth flow behaves, completes the task, loses that model when the session ends. Chat history isn't a great system of record. After research, planning should start with a clean context. Ask which files the approaches touch, which invariants they preserve, how you'd reverse them. A human picks the path. Implementation should stop if it discovers the map was wrong. Review starts fresh, working backward from acceptance criteria—a clean reviewer notices when a test proves the implementation while missing the requirement.

Then comes the harness. Instructions record unusual facts. Skills package reusable procedures. Plugins govern access to ownership catalogs, incident archives, dashboards. The harness is the working environment around the agent: context, tools, permissions, tests, logs, recovery. When the agent gets something wrong, the test is what happens next. If you quietly repair the diff, the next session repeats it. When the same review comment appears again, move it into a lint rule, hook, type, test, or skill. A deny rule, scoped credential, or CI check doesn't have to remember. Over time the harness becomes a record of failures the team decided not to pay for twice.

Finally: start with zero-risk work. Lock today's behavior before anything improves it. Characterization tests document what the module does today, ugly parts included, because in an old system some of that ugliness is what the business runs on. Netflix used the same idea at production scale during its GraphQL cutover: replay and shadow traffic against the old and new paths, diff the payloads, promote only when they match. When an agent is the one making tests pass, don't let that same session be the only author. Pin the behavior first in a separate pass or by a person. Then let the agent work. Otherwise you get a green suite that encodes the implementation you just invented.

The throughline here is visibility. Brownfield codebases are not information-complete. The system design, the trade-offs, the non-obvious constraints—they live in heads and in the operational history, not in the tree. Agents can infer a lot from code, but not the unwritten rules. The safer the agent, the better you've made those rules visible and the better you've built a harness that enforces them without needing an engineer to remember them. The faster you can make changes safely, the less you're paying for the complexity of age. That's the real win.
