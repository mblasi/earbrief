Brian Houck de DX pregunta la pregunta que precede a todas las otras: qué estaba resolviendo code review antes de que IA llegara?

Los números son sobering. En Meta, líneas de código por human diff saltaron ciento seis por ciento year over year. Diffs por developer por mes subieron cincuenta y uno por ciento. Ochenta por ciento vino de IA agentic. Mientras tanto, diffs revieweadas dentro de veinticuatro horas están declining. En algunos grandes grupos, reviewers enfrentan thousands de pending reviews.

Las matemáticas están rotas. Developers quieren gastar acerca de siete por ciento de su tiempo en review. IA está generando suficiente código que requeriría diez veces eso. No puedes pedir a humanos que se muevan más rápido. Así que la pregunta se vuelve: qué perdemos si automatizamos review away?

Aquí está lo que Brian encontró: developers identificaron defect detection como la razón primaria para code review. Pero defect-related comments compusieron solo catorce por ciento de actual review comments. En práctica, code review sirve muchos otros propósitos. Más que la mitad de developers usan reviews para explorar soluciones alternativas. Muchos señalaron a knowledge transfer y gaining awareness de qué teammates están construyendo.

El visible output de code review es mejor código. El invisible output es una mejor organización de ingeniería.

Esta es la distinción que Brian está pusheando contra el mundo tech para entender. Code review es cómo equipos construyen shared understanding de un sistema. Es cómo developers junior aprenden de experienced ones. Es cómo architectural intent obtiene surfaced, cuestionado, y refinado. Es cómo mental model de un ingeniero se vuelve el mental model del equipo.

Organizaciones no se vuelven resilientes porque una persona entiende un subsystem. Se vuelven resilientes porque muchas lo hacen.

Así que cuando sistema RADAR de Meta landa trescientos treinta mil diffs con un tercio del revert rate y uno-fiftieth del production incident rate, eso es operationally stunning. Pero qué significa para ingenieros que no vieron esos diffs? Qué no aprendieron? Qué mental models no fueron shared? Qué preguntas nunca fueron hechas porque el código auto-mergeó mientras la gente estaba en meetings?

Brian no es anti-automation. Es pro-deliberation. La solución no es pedir a humanos que revisen más rápido. Es pedir: qué cambios realmente merecen atención humana? Cuáles necesitan human judgment, no solo verification? Cuáles necesitan ser vistos porque enseñan algo?

Él llama esto la diferencia entre code review como gate y code review como forum. Gating es about safety. Forum es about learning. IA puede gatekeep efectivamente. Pero no puede reemplazar el forum.

La verdad incómoda es que muchas organizaciones han estado ignorando buenas prácticas de code review por años. Keep changes pequeños. Escribe meaningful descriptions. Corre automated checks antes de pedir humanos. Review frecuentemente, en bounded sessions. Selecciona reviewers que conocen el código.

Research de dos mil dieciséis mostró que timely feedback, review size, y understanding del motivation para change eran los top tres challenges. Esa research fue una década vieja antes de que IA llegara. Los problemas no eran nuevos. Fueron simplemente ignorados a escala.

IA no creó esta crisis. La heredó y la amplificó.

Así que el argumento de Brian es surgical: antes de pedir IA que arregle code review, pregunta si tu equipo construyó los habits que hacen code review efectivo en primer lugar. Small changes. Protected reviewer time. Automated routine checks así humanos focusan en judgment.

Una vez que esos fundamentales están en lugar, IA tiene un rol. Los developers que DX entrevistó no quieren que review desaparezca. Quieren que IA remueva las partes que no requieren human judgment así human attention puede ir donde importa. Catch security issues. Flag high-risk changes. Surface impact. Handle routine. Deja humanos hacer judgment.

El modelo RADAR camina esa línea. Low-risk changes auto-merge. High-risk changes van a humanos. Un sistema stratified en lugar de un binary gate.

Pero la pregunta permanece: conforme automation se expande, qué se pierde? El equipo RADAR lo reconoce explícitamente. Automated review mejora efficiency. Pero podría sufrir knowledge transfer. Eso es un tradeoff worth monitoring.

El final move de Brian es el más importante. No preguntes "¿funciona?" Pregunta "¿cómo maximiza el tiempo y valor del human judgment?" Esa es la métrica que importa cuando IA entra al review process.
