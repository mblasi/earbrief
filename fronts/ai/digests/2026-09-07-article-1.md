Most of what an AI coding agent does is not thinking. It is input and output. Reading five files to answer a question about one method. Generating a test file that follows the exact same pattern as the twenty test files sitting next to it. Updating documentation after a meeting. Thousands of tokens spent, almost zero reasoning happening, and every one of those tokens billed to a frontier model that is wildly overqualified for the job. A Spotify engineer wrote up how they cut Claude Code's token usage by roughly ninety percent, and the mechanism is not a new subscription or a platform rebuild. It is routing.

The economic pressure behind this is not hypothetical. Gartner projects that by 2028, AI coding costs will surpass the average developer's salary. A quarter of engineering leaders already spend two hundred to five hundred dollars per developer per month on tokens, and some organizations are well past two thousand. The tooling still pays for itself, but only if teams stop burning frontier-model tokens on work that does not require frontier reasoning.

The fix here rests on a feature called AiKA Modes in Portal by Spotify, an internal developer platform. A mode is a declarative agent that runs on an ephemeral runtime, conceptually similar to a serverless function but for agents. You define instructions, pick a model, set parameters like temperature, and attach tools. The platform handles everything else, and modes can be called from a command line interface, shared publicly across a company, or kept private.

Two modes do the actual work. The first, called bulk-reader, exists for moments when Claude would otherwise read multiple large files just to answer a single question. It runs on a cheaper model, in this case Gemini two point five Flash, with instructions to behave as a precise code analyst: read the files, answer concisely, output structured bullets only, skip anything not asked for. The second mode, code-writer, handles boilerplate: tests, configuration scaffolding, type stubs, anything where the output is predictable from existing patterns in the codebase. Both modes are instructed to produce clean output with no markdown fences or conversational padding, because without that constraint the worker model wraps everything in prose that Claude then has to parse through anyway, defeating the purpose.

The interesting engineering problem was not the modes themselves but getting Claude Code to actually use them. The first version was a block of routing rules pasted into a CLAUDE.md file, and it sort of worked, but the rules were advisory. Claude could read them and ignore them, and every project needed its own copy. The version that stuck is a Claude Code plugin with three layers. The first layer is hooks that fire before every tool call: if a file read exceeds a configurable line threshold, the hook blocks the read outright and tells Claude to delegate instead. Targeted reads, where Claude already knows which section it needs, pass through untouched. The second layer is a pair of scripts that wrap the platform's command-line calls, building requests, unwrapping errors, and reporting token usage. The third layer is skill files that tell Claude when and how to invoke those scripts. The layering matters because it degrades gracefully — even if Claude never reads the skill description, the hook still blocks the expensive read, so the system holds even when the softer instruction layer fails.

Tested against a Java monorepo across four scenarios, the mean savings on bulk-read operations came out around ninety percent. The code-write case is harder to quantify precisely, because without the delegation, Claude both reads the reference files and generates the output as expensive output tokens; with delegation, the generated code goes straight to disk and Claude never sees it at all.

The limitations are as instructive as the wins. You cannot delegate editing, because the worker model's summaries do not carry reliable line numbers, so any edit still requires Claude to read the specific section directly — this is why targeted reads with offset and limit are allowed to bypass the hook. You cannot delegate reasoning either: in testing, the worker model caught surface-level patterns but missed a subtle thread-safety bug that Claude spotted immediately once given the right context, which is why debugging, architectural decisions, and safety-critical code are explicitly excluded from the routing. And latency adds up, since every delegation is a network round trip through the platform to the worker model and back, typically ten to thirty seconds — fine for large reads, counterproductive for small ones, which is exactly why the line-count threshold exists in the first place.

The deeper point the author makes is that the token savings are a side effect of a more durable idea: model routing as a configuration problem rather than a systems engineering problem. The modes are reusable across every project, shareable company-wide, and composable — a documentation-writer mode, a code-review-summary mode, a translation mode are each just a few clicks away rather than new infrastructure. And critically, the modes decouple the routing decision from the worker: the plugin decides when to delegate, the mode decides how to respond, and swapping the underlying cheap model requires no change to the plugin at all. That separation is what turns a clever cost hack into an actual architecture pattern other teams can copy without rebuilding it from scratch.
