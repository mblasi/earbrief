El paper de Meta sobre RADAR, submiteado Mayo veintiocho y revisado Junio doce, es la respuesta de trabajo a lo que Rachel Laycock estaba cuestionando: cómo manejas code review cuando agents están produciendo más código que humanos pueden realísticamente revisar?

El contexto es stark. En Meta, líneas de código significativas por human-landed diff crecieron ciento cinco punto nueve por ciento year over year. Per-developer diff volume subió cincuenta y uno por ciento. IA agentic fue responsable de ochenta por ciento del crecimiento. Mientras tanto, la share de diffs recibiendo timely review declinó. Code supply excedió reviewer bandwidth por órdenes de magnitud.

En lugar de hiring más reviewers o esperar código más lento generation, Meta construyó RADAR: Risk Aware Diff Auto Review. Es un multi-stage funnel que clasifica cada diff por authorship y source type, aplica eligibility gates, static heuristics, un machine-learned Diff Risk Score, LLM-based automated code review, y deterministic validation antes de landing.

El key insight: no todos los diffs necesitan el mismo scrutiny. Un style fix de un ingeniero experimentado en un archivo non-critical es low-risk. Un cambio arquitectónico fundamental affecting core infrastructure es high-risk. RADAR stratifica por risk y aplica automation proportionally.

Los resultados son telling. RADAR revisó quinientos treinta y cinco mil plus diffs y landing trescientos treinta y uno mil. Cuando relaxaron el Diff Risk Score threshold de veinticinco a cincuenta percentile, el approve rate subió a sesenta punto treinta y uno por ciento. El revert rate para RADAR-reviewed diffs era un tercio de non-RADAR diffs. El production incident rate era uno-fiftieth.

Aquí es donde se pone interesante. Las implicaciones de latencia son dramáticas. RADAR redujo median time to close por over trescientos treinta por ciento. Median diff review wall time droppeó treinta y cinco por ciento. Ingenieros no estaban esperando más. El bottleneck se disolvió.

El sistema no está solo automatizando code review. Está automatizando away la ceremony. La parte de LLM checkea por code logic, security concerns, style violations. La parte deterministic maneja linting y known patterns. La parte de risk scoring decide si human review es incluso necesaria.

Lo que está unstated pero obvious: esta es la respuesta Rachel Laycock estaba moviéndose hacia. No haces code review más rápido. Haces code review innecesario para los diffs que no lo necesitan. Reservas human judgment para los lugares donde realmente importa. Stratificas por risk así que un security-critical change todavía obtiene un human, pero un boring refactor landing automáticamente.

El paper es careful acerca de safety. El production incident rate siendo uno-fiftieth sugiere el risk model está working. Pero aquí está la implicación Rachel levantó: RADAR todavía está centered en code review. La assumption es todavía que code landing después de review. Qué si en su lugar, te muevas a trunk-based development con continuous verification? Qué si las conversaciones importantes ocurrieran durante design, no después de implementación?

El approach de Meta es pragmático y operational. Resuelve el immediate bottleneck. Pero todavía trata code review como el primary gate. Rachel pushearía más: qué si la gate en sí es incorrect?

Dicho eso, este paper es mandatory reading para anyone construyendo sistemas para manejar AI-generated code a escala. El risk stratification approach es clean. Las métricas son rigorous. Y demuestra que automation no tiene que ser binary. Puedes tener automated approval, human review, y automated rejection en el mismo funnel, tuned por actual risk distribution.

La lección práctica: cuando humanos no pueden keep up con máquinas, no intentes hacer humanos más rápidos. Cambia el proceso así la mayoría de cosas no necesitan humanos. Reserva humanos para decisiones actuales.
