You've probably felt it: you point a powerful agent at a complex task, and within minutes it has painted itself into a corner, made a decision you didn't intend, or simply lost track of what it was supposed to be doing. The promise of multi-agent systems has always been that collaboration would solve this — let one agent handle specification while another handles cleanup while a third does the architecture — but in practice it usually degrades into a chaotic free-for-all where everyone talks over everyone else and nothing gets finished.

Robert Martin, better known as Uncle Bob, has been quietly working on a different approach. His project SwarmForge, which just passed 2,100 stars on GitHub and 258 commits, doesn't try to build an intelligent orchestrator that decides what each agent should do next. Instead, it takes the opposite route: it creates a disciplined structure where agents hand off work to each other in a predictable sequence, with clear boundaries of responsibility, enforced by tmux sessions, git worktrees, and a shared constitution.

The system runs entirely locally. It needs zsh, git, tmux, Babashka, and at least one agent backend like Codex, Claude, or Copilot. You choose a workflow branch — two-pack, four-pack, or six-pack — that defines which roles participate and in what order they pass tasks. Then you run the single command `./swarm`, and a tmux session spawns with one window per role, each agent working in its own git worktree so they never step on each other's changes.

The two-pack is the quick backend loop. A coder agent implements what you want using TDD and unit tests, then hands off to a cleaner agent that does cleanup, CRAP and DRY review, architectural review, and hardening. The normal flow is simply coder to cleaner back to coder until both agree the work is done. It's designed for tasks where you want fast iteration without the overhead of specification and acceptance testing.

The four-pack adds a specifier role that turns your intent into precise Gherkin acceptance specifications and asks for approval before anyone writes a line of code. Then the coder implements those specifications with TDD and generated acceptance tests, followed by a refactorer that handles behavior-preserving cleanup and coverage improvement, and finally an architect who owns the high-level structure and dependency direction. The flow cycles through specifier, coder, refactorer, architect, and back, each agent working in its own worktree with the previous agent's completed changes merged in via git.

The six-pack is the full treatment for major projects. It splits every quality-concern role into its own agent: the specifier writes Gherkin specs and end-to-end QA procedures, the coder implements them with TDD, the cleaner does local cleanup and mutation-site scans, the architect reviews module structure and boundaries, the hardender handles mutation and language hardening, and a separate QA agent converts the specifier's procedures into executable scripts and runs final verification. Six agents, each doing one job well, passing work down a pipeline.

What makes this work where other multi-agent setups fail is the message-passing layer between the roles. Rather than having agents communicate directly with each other through prompts, SwarmForge uses a handoff protocol. Each agent writes its work into its git worktree and produces a structured handoff message that the next agent picks up. The handoff includes the current state, what was completed, what remains, and any concerns or decisions that need to carry forward. The next agent starts fresh in its own clean worktree, reads the handoff, and proceeds.

The tmux sessions and worktrees are not incidental — they are the core mechanism for isolation. Each agent runs in its own tmux window attached to its own session, in its own git worktree, so there is no shared editing state, no accidentally clobbered files, and no ambiguity about who owns which part of the codebase at any given moment. When an agent finishes its turn, it commits to its worktree and writes a handoff message. The next agent's window lights up, pulls the changes, and starts its review.

The constitution articles embedded in the system provide the shared rules that all agents follow — coding standards, review criteria, communication protocols — and these articles update as the project evolves. Each workflow branch ships with its own local constitution on top of the shared articles from the main branch, so teams can customize behavior without rewriting the core system.

The README acknowledges upfront that this is a system for disciplined engineering, not for casual hacking. It requires you to set up agent backends, configure terminal adapters for your specific terminal emulator, and understand git worktrees. The barrier to entry is real. But that is precisely the point: the discipline is the feature, not a bug.

What's most interesting about SwarmForge is what it doesn't build. There is no central AI director deciding who should do what next. There is no reinforcement learning loop optimizing handoff efficiency. There is no dynamic task graph that rebalances workloads. Instead, it leans on the things that have worked reliably in software engineering for decades: explicit process, immutable handoffs, isolated environments, and clear role boundaries. The agents are smart, but the process is dumb in the best way.

This approach matters right now because as agent tooling gets more capable, the temptation is to throw more agents at harder problems and hope they figure it out. SwarmForge argues for the opposite: give each agent a narrow, well-defined job, structure the handoffs so nothing is lost in translation, and let git — not an LLM — be the arbiter of what happened when. It is a system designed not around what AI can do, but around what reliable engineering has always demanded.
