La vez pasada en este track trazamos un request de punta a punta y te hice una promesa. Te dije que dentro de cada transformer block pasan exactamente dos cosas: attention, donde los tokens se hablan entre sí, y una red feed-forward, donde cada token piensa en privado. Y te dije que attention es donde ocurre el contexto, pero manoteé el mecanismo y te dije que íbamos a volver. Esto es nosotros volviendo. Para el final de este episodio vas a poder computar un paso de attention con números lo bastante chicos como para tenerlos en la cabeza, vas a saber exactamente por qué el contexto largo es cuadrático antes incluso de llegar al problema de memoria, y vas a entender qué está comprando realmente la grouped-query attention cuando la lees en un model card.

Empecemos por el problema que attention existe para resolver, porque el mecanismo solo tiene sentido una vez que sientes la necesidad de él.

Recuerda de la vez pasada: después del lookup de embeddings, cada token es un vector, un punto en un espacio de muchas dimensiones, y ese punto de partida codifica el significado de diccionario del token, sin contexto. La palabra "bank" arranca en el mismo lugar ya sea que la oración hable de ríos o de dinero. Todo el trabajo de las capas es mover el vector de cada token hacia donde le corresponde dadas las palabras a su alrededor. Pero acá está el detalle que hace esto difícil. La red feed-forward procesa cada token de forma completamente independiente. Nunca mira a la izquierda ni a la derecha. Así que si las capas van a usar contexto, tiene que haber un lugar específico donde un token tenga permitido estirarse hacia los otros tokens y traerse lo que necesita. Ese lugar, el único lugar en toda la arquitectura donde la información se mueve entre posiciones, es attention. Todo lo demás en el transformer trata a tus tokens como una bolsa de vectores independientes. Attention es el único canal a través del cual se vuelven una secuencia.

Entonces, ¿qué significa realmente, mecánicamente, "estirarse y traerse información"?

Acá está la metáfora que mapea limpio sobre la matemática, y después hacemos la matemática. Piensa en una biblioteca, o honestamente, piensa en una búsqueda. Cada token puede hacer tres cosas. Puede hacer una pregunta — esa es su query. Puede publicitar de qué se trata — esa es su key. Y puede ofrecer contenido si lo eligen — ese es su value. Query, key, value. La palabra "bank", ahí sentada ambigua, emite una query que en efecto dice "soy un sustantivo que necesita un tema — ¿hay alguien acá sobre geografía o sobre finanzas?". Mientras tanto la palabra "river", unas posiciones atrás, publicita una key que dice "soy sobre agua y paisaje". Cuando la query de bank se alinea bien con la key de river, bank se trae el value de river, y el value es la información concreta que desplaza a bank hacia la región del espacio de la orilla del río. Ese es un paso de attention. Cada token hace esto simultáneamente, cada uno haciendo su propia pregunta y obteniendo su propia mezcla a medida de los values de todos los demás.

Ahora, ¿de dónde salen la query, la key y el value? Esta es la parte que la gente se saltea, y es el meollo. Los tres se derivan del mismo vector de entrada, multiplicándolo por tres matrices de pesos aprendidas y separadas. Llamémoslas W-query, W-key y W-value. El vector de cada token entra; salen tres vectores nuevos, su query, su key y su value. Estas tres matrices son los parámetros reales — son lo que el modelo aprendió durante el entrenamiento. Al modelo nunca le dijeron cómo debía verse una query. Descubrió, a lo largo de billones de tokens, que proyectar la entrada de una forma para hacer una query y de otra forma para hacer una key, de modo que los tokens relevantes produzcan queries y keys que apunten en direcciones parecidas, es una buena forma de reducir el error de predicción. La metáfora de la biblioteca es algo que imponemos después para darle sentido. El modelo simplemente encontró tres matrices que funcionan.

Una sutileza acá hace tropezar a casi todos, así que matémosla ahora: ¿por qué la key y el value son separados? ¿Por qué no usar un solo vector tanto para ser comparado como para ser entregado? Porque publicitar y entregar son trabajos distintos. La key es cómo un token se promociona para ser recuperado — las dimensiones que lo hacen encontrable. El value es lo que efectivamente aporta una vez encontrado. Un token podría publicitar "soy sobre finanzas" con su key, en la forma compacta que haga eficiente el matching, pero el value que entrega podría ser un paquete de información mucho más rico que el token receptor incorpora dentro de sí. Separar los dos deja que el modelo optimice la encontrabilidad y la contribución de forma independiente, y — esto importa en un segundo — es la key y el value, no la query, lo que se cachea durante la generación, porque eso es lo que los tokens pasados le ofrecen a los futuros. La query es descartable; la computas, la usas una vez, la tiras.

Pongámosle números, porque te prometí números.

Imagina un modelo de juguete donde cada vector de token tiene apenas cuatro dimensiones, y tenemos una secuencia de tres palabras: "the", "cat", "sat". Así que tenemos tres vectores de entrada, cada uno con cuatro números. Multiplicamos cada uno por W-query para obtener tres vectores query, por W-key para obtener tres vectores key, por W-value para obtener tres vectores value. Para que siga entrando en la cabeza, digamos que los vectores query y key también tienen cuatro dimensiones. Ahora la operación central. Para que la palabra "sat" descubra a qué prestarle attention, tomamos su vector query y computamos su dot product con cada vector key de la secuencia — la key de "the", la key de "cat", y su propia key. Un dot product es simplemente multiplica-los-números-que-se-corresponden-y-súmalos; es un solo número que mide qué tan alineados están dos vectores. Así que "sat" obtiene tres números, un score por token, midiendo cuánto matchea su pregunta con la publicidad de cada token. Score alto, match fuerte. Eso es todo. Ese es el corazón de attention: una query dotteada contra cada key, produciendo un score de relevancia por posición.

Hazlo dolorosamente concreto por un momento. Supón que la query de "sat", dotteada contra las tres keys, da dos coma uno para "cat", cero coma cuatro para "the", y uno coma seis para su propia key. Tres números simples. "Cat" sacó el más alto, que es lo que esperarías — lo que está sentado es el gato. No está pasando nada misterioso; es literalmente multiplicar-y-sumar produciendo un número más grande cuando dos vectores apuntan en la misma dirección. Toda la inteligencia de la operación vive en las matrices de pesos que produjeron esas queries y keys en primer lugar. El dot product en sí es aritmética de primaria. Aférrate a eso, porque desmitifica todo el asunto: attention es una búsqueda de similitud aprendida, implementada con la operación más barata del edificio.

Ahora tres cosas chicas pero que cargan el peso les pasan a esos scores antes de ser usados.

Primera, el scaling. Esos scores crudos de dot product tienen un problema estadístico. Cuantas más dimensiones tengan tus vectores query y key, más grandes tienden a salir los dot products, puramente como cuestión de aritmética — estás sumando más términos, así que el total se dispersa más lejos de cero. Concretamente, si los números que entran tienen varianza de uno, el dot product de dos vectores de, digamos, ciento veintiocho dimensiones sale con una varianza de ciento veintiocho. ¿Por qué importa? Porque el siguiente paso es un softmax, y el softmax es exquisitamente sensible a la escala de sus entradas. Aliméntalo con números muy separados y se satura: le entrega esencialmente todo el peso al único score más grande y aplasta a todo lo demás a casi cero. Un softmax saturado casi no tiene gradiente, así que el modelo no puede aprender. La solución es vergonzosamente limpia: divide cada score por la raíz cuadrada de la dimensión de la key. Si la varianza era ciento veintiocho, dividir por la raíz cuadrada de ciento veintiocho la trae de vuelta a uno, justo donde el softmax se porta bien. Por eso se llama scaled dot-product attention, y esa pequeña división por una raíz cuadrada, que parece una nota al pie, es la diferencia entre un modelo que entrena y uno que no.

Segunda, el softmax. Tomamos esos tres scores escalados y los empujamos por el softmax, que convierte cualquier conjunto de números en un conjunto de pesos positivos que suman uno. Ahora "sat" tiene, digamos, setenta por ciento de su attention en "cat", veinte por ciento en "the", diez por ciento en sí mismo — una distribución de probabilidad limpia sobre dónde mirar. Esos son los attention weights.

Tercera, el premio. Tomamos esos weights y computamos un promedio ponderado de los vectores value. Setenta por ciento del value de "cat", veinte por ciento del value de "the", diez por ciento del value de "sat", sumados en un solo vector nuevo. Ese vector mezclado es lo que attention devuelve para el token "sat". Literalmente mezcló información de los tokens que decidió que eran relevantes, en las proporciones que decidió. Haz eso para cada token en paralelo y completaste una operación de attention. Query dotteada con keys, escalada, pasada por softmax a weights, weights aplicados a values. Cuatro pasos. Ten esa forma en la cabeza, porque todo lo demás es una variación de ella.

Ahora, tres refinamientos convierten ese juguete en la cosa que corre en producción, y cada uno tiene una consecuencia de ingeniería directa.

Refinamiento uno: causal masking. En un modelo que genera texto, un token nunca puede tener permitido prestarle attention a tokens que vienen después de él — cuando estás prediciendo la palabra cinco, la palabra seis no existe todavía, y si el modelo pudiera espiarla durante el entrenamiento, aprendería a hacer trampa y después se caería a pedazos en inferencia cuando no hay nada que espiar. Así que se lo prohibimos. Mecánicamente, esto es deliciosamente brusco: después de computar la matriz de scores, antes del softmax, tomamos cada score que corresponde a una posición futura y lo ponemos en menos infinito. Cuando menos infinito pasa por el softmax, se vuelve exactamente peso cero. El token literalmente no puede ver el futuro porque anulamos su capacidad de hacerlo. Esto se llama causal masking, y acá está por qué debería importarte como ingeniero. La máscara es lo que permite que el entrenamiento sea paralelo. Como cada posición solo puede ver el pasado, el modelo puede procesar una secuencia de entrenamiento entera — predecir cada próximo token en cada posición — en un solo forward pass, con la máscara garantizando que cada predicción solo usó contexto anterior legítimo. Sin la máscara tendrías que entrenar una posición a la vez. La máscara triangular es la razón callada de que puedas entrenar un transformer sobre un billón de tokens siquiera.

Refinamiento dos, y este es el grande: múltiples heads. Todo lo que describí hasta acá es un solo attention head — un conjunto de matrices query, key y value, computando un tipo de relevancia. Pero un head solo puede aprender una noción de "relevante". Quizá aprende a rastrear sintaxis, matcheando verbos con sus sujetos. Pero también quieres un head rastreando el tema de largo alcance, y uno rastreando qué pronombre se refiere a qué sustantivo, y uno rastreando patrones posicionales. Así que los modelos reales corren muchos attention heads en paralelo — un modelo grande podría tener sesenta y cuatro por capa. Cada head tiene sus propias matrices query, key y value más chicas y opera en su propia rebanada del espacio de vectores, computando sus propios scores, su propio softmax, su propia mezcla ponderada de values, completamente independiente de los demás. Es genuinamente paralelo — los heads no se hablan durante la operación. Después de que todos los heads terminan, sus vectores de salida se concatenan de nuevo y se pasan por una matriz de salida final que los mezcla en un solo resultado. Esto es multi-head attention, y el modelo mental es: sesenta y cuatro lentes independientes, cada uno buscando un tipo distinto de relación, todos leyendo la misma secuencia a la vez, y después sus hallazgos se fusionan. La consecuencia de ingeniería es que el costo en parámetros y cómputo de attention escala con la cantidad de heads, y — como veremos en un segundo — el costo de memoria del serving también, que es exactamente la presión que produjo las variantes modernas.

Refinamiento tres: el costo, y acá es donde este episodio se conecta con todo el resto de tu vida en inferencia. Mira de nuevo la operación central. Cada token computa un score contra cada otro token. Si tienes mil tokens, eso es mil por mil — un millón de scores. Diez mil tokens, cien millones de scores. La matriz de scores es cuadrada en el largo de la secuencia. Esto es lo que la gente quiere decir cuando dice que attention es cuadrática. Duplica tu contexto, cuadruplica el cómputo de attention. Este único hecho es la razón profunda de que el contexto largo sea caro, y fíjate que es un costo distinto del que discutimos el episodio pasado. La vez pasada, el KV cache era un problema de memoria que crece linealmente con el largo de la secuencia. Este — la matriz de scores — es un problema de cómputo que crece cuadráticamente. El contexto largo te pega dos veces, en dos monedas distintas, y saber cuál es cuál es la diferencia entre adivinar y diagnosticar cuando estás mirando un gráfico de latencia.

Voy a señalar una cosa acá y dejarla para un episodio posterior, porque vale la pena saber que la salida de emergencia existe. Esa matriz de scores cuadrática suena como que tiene que construirse entera, todas las entradas, el millón o los cien millones, sentadas en memoria a la vez. Por años fue así, y esa matriz materializada era un segundo costo de memoria brutal encima del cómputo. El algoritmo llamado flash attention rompió esa suposición computando attention en tiles, streameando por la secuencia y sin almacenar nunca la matriz de scores completa, llevando totales corrientes en su lugar. No cambia el cómputo cuadrático — igual haces todos los multiplica-y-suma — pero elimina la explosión cuadrática de memoria de la matriz intermedia y, de yapa, corre mucho más rápido al quedarse en la parte rápida del chip. Vamos a desarmar ese cuando lleguemos al track de hardware. Por ahora, solo archívalo: el cómputo es inevitable, pero la explosión de memoria de la matriz de scores era un detalle de implementación, y alguien lo arregló.

Lo que nos trae a las variantes que efectivamente ves en los model cards, y ahora tienes exactamente la maquinaria para entenderlas.

Volvamos al KV cache del episodio pasado. Recuerda, para evitar recomputar el pasado en cada token generado, cacheamos los vectores key y value de cada token que ya procesamos. Ahora cuenta el costo con precisión. En multi-head attention pura, cada uno de esos sesenta y cuatro heads tiene sus propias keys y sus propios values, así que estás cacheando sesenta y cuatro conjuntos separados de vectores key y value por cada token del contexto. Para contextos largos y batches grandes, ese cache se vuelve el mayor consumidor individual de memoria de GPU durante el serving — más grande, muchas veces, que los pesos del modelo mismo. Es el cuello de botella.

Así que acá está la jugada, y es hermosa en su tacañería. ¿Y si los heads compartieran? La intuición es que las queries son donde vive la mayor parte de la diversidad útil — quieres sesenta y cuatro preguntas distintas siendo hechas — pero las keys y los values se pueden compartir entre grupos de heads sin lastimar mucho la calidad. Esto es grouped-query attention. Mantienes los sesenta y cuatro query heads, así que el modelo sigue haciendo sesenta y cuatro preguntas distintas, pero tienes solo, digamos, ocho conjuntos de keys y values, cada uno compartido por un grupo de ocho query heads. El resultado: el KV cache se encoge por un factor de ocho, porque estás almacenando ocho conjuntos de keys y values por token en vez de sesenta y cuatro. Esa es exactamente la configuración que usa el modelo de setenta mil millones de parámetros de Llama tres — sesenta y cuatro query heads, ocho key-value heads, una reducción de ocho veces en el tamaño del cache — y ahora es el default en la mayoría de los modelos abiertos modernos. Llévalo al extremo, donde todos los query heads comparten un único conjunto de keys y values, y obtienes multi-query attention, máximo ahorro de memoria, un poco más de pérdida de calidad. Grouped-query es el punto dulce en el que la industria se asentó: casi la memoria de la versión agresiva, casi la calidad de la versión completa.

Siente lo que acaba de pasar ahí. Grouped-query attention no es alguna idea nueva y profunda. Es una respuesta directa, casi mecánica, a que el KV cache sea el cuello de botella — el mismísimo cuello de botella que identificamos el episodio pasado. Una vez que sabes que las keys y los values son lo que cacheas, y que los heads son lo que multiplica el cache, compartir keys y values entre heads es la palanca obvia. Ese es todo el punto de este track: cuando entiendes el mecanismo, las decisiones de ingeniería dejan de ser conjuros mágicos de un model card y empiezan a ser jugadas obvias dadas las restricciones.

Déjame aterrizar esto con las tres conclusiones que vale la pena guardar.

Uno. Attention es el único lugar donde los tokens interactúan, y su mecanismo son cuatro pasos que ahora puedes recitar: cada token se proyecta en una query, una key y un value; cada query se scorea contra cada key con un dot product; los scores se escalan y se pasan por softmax a weights; y esos weights mezclan los values en el nuevo vector del token. Todo lo demás en el transformer trata a los tokens de forma independiente. Si recuerdas una sola forma, recuerda query-key-value.

Dos. Attention te cuesta en dos monedas separadas, y no son la misma moneda. La matriz de scores es cuadrática en el largo de la secuencia — eso es cómputo, y es por qué duplicar el contexto cuadruplica el trabajo de attention. El KV cache es lineal en el largo de la secuencia pero multiplicado por la cantidad de key-value heads — eso es memoria, y es lo que grouped-query attention existe para encoger. Cuando el contexto largo esté lento, pregúntate cuál de los dos te está mordiendo.

Tres. Las variantes del model card — multi-head, grouped-query, multi-query — son todas la misma operación de cuatro pasos con un único dial: cuántas keys y values guardas versus cuántas queries haces. Más compartir, menos memoria, un poco menos de calidad. Ese único dial explica a toda la familia, y ahora la puedes leer con fluidez.

Lo próximo en este track vamos más a fondo en el KV cache mismo — cómo se acomoda en la memoria, por qué el manejo ingenuo desperdicia la mayor parte de tu GPU, y qué hizo la paged attention al respecto. Ahora entiendes las keys y los values lo bastante bien como para que el cache se sienta menos como almacenamiento y más como el muro de carga de todo el stack de serving. Nos vemos ahí.
