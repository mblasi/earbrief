Meta's paper on RADAR, submitted May twenty-eight and revised June twelfth, is the working answer to what Rachel Laycock was questioning: how do you handle code review when agents are producing more code than humans can realistically review?

The context is stark. At Meta, significant lines of code per human-landed diff grew one hundred five point nine percent year over year. Per-developer diff volume rose fifty-one percent. Agentic AI was responsible for eighty percent of that growth. Meanwhile, the share of diffs receiving timely review declined. Code supply exceeded reviewer bandwidth by orders of magnitude.

Instead of hiring more reviewers or waiting for slower code generation, Meta built RADAR: Risk Aware Diff Auto Review. It's a multi-stage funnel that classifies each diff by authorship and source type, applies eligibility gates, static heuristics, a machine-learned Diff Risk Score, LLM-based automated code review, and deterministic validation before landing.

The key insight: not all diffs need the same scrutiny. A style fix from an experienced engineer on a non-critical file is low-risk. A fundamental architectural change affecting core infrastructure is high-risk. RADAR stratifies by risk and applies automation proportionally.

The results are telling. RADAR reviewed five hundred thirty-five thousand plus diffs and landed three hundred thirty-one thousand. When they relaxed the Diff Risk Score threshold from the twenty-fifth to the fiftieth percentile, the approve rate climbed to sixty point thirty-one percent. The revert rate for RADAR-reviewed diffs was one-third that of non-RADAR diffs. The production incident rate was one-fiftieth.

This is where it gets interesting. The latency implications are dramatic. RADAR reduced median time to close by over three hundred thirty percent. Median diff review wall time dropped thirty-five percent. Engineers weren't waiting anymore. The bottleneck dissolved.

The system isn't just automating code review. It's automating away the ceremony. The LLM part checks for code logic, security concerns, style violations. The deterministic part handles linting and known patterns. The risk scoring part decides whether human review is even necessary.

What's unstated but obvious: this is the answer Rachel Laycock was moving toward. You don't make code review faster. You make code review unnecessary for the diffs that don't need it. You reserve human judgment for the places where it actually matters. You stratify by risk so that a security-critical change still gets a human, but a boring refactor lands automatically.

The paper is careful about safety. The production incident rate being one-fiftieth suggests the risk model is working. But here's the implication Rachel raised: RADAR is still centered on code review. The assumption is still that code lands after review. What if instead, you moved to trunk-based development with continuous verification? What if the important conversations happened during design, not after implementation?

Meta's approach is pragmatic and operational. It solves the immediate bottleneck. But it still treats code review as the primary gate. Rachel would push further: what if the gate itself is wrong?

That said, this paper is mandatory reading for anyone building systems to handle AI-generated code at scale. The risk stratification approach is clean. The metrics are rigorous. And it demonstrates that automation doesn't have to be binary. You can have automated approval, human review, and automated rejection in the same funnel, tuned by actual risk distribution.

The practical lesson: when humans can't keep up with machines, don't try to make humans faster. Change the process so most things don't need humans. Reserve humans for actual decisions.
