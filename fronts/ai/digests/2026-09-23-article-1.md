Rachel Laycock, CTO at Thoughtworks, wrote something heretical on September second: maybe code review isn't the problem. Maybe code review is how we've been solving the wrong problem all along.

The trigger was a panel with Brian Houck from DX at Code Remix. Brian argued that AI is producing more code than humans can review. At Meta, lines of code per human diff increased one hundred six percent in a year. Pull request sizes grew sixty-four percent. His worry: we'll automate code review away and lose knowledge transfer, junior mentoring, and collective ownership. Rachel's response: why are we waiting until code review to do those things?

This is a surgical critique of how software teams actually work in 2026. For two decades, the pull request became the center of everything. Write code, finish it, package it, throw it over the wall, then have the important conversation about whether it was the right thing in the right way. Rachel hates this. She's lost too many hours to merge conflicts arguing about the governance model itself.

Her principle is ancient and solid: shorten feedback loops. If feedback is valuable, don't remove it. Move it earlier. So if you want to explore alternative solutions, do it before implementing one. If you want knowledge transfer, pair program. If you want junior engineers to learn how experienced engineers think, let them work with experienced engineers while they're thinking, not afterwards when everything is done and crystallized in a diff.

The argument extends to collective ownership. Don't rely on pull requests to tell people what someone else already built. Organize teams to build and operate software collectively. Use pairing, mob programming, design sessions on whiteboards. These create ownership earlier, before the code exists.

For architectural alignment, design together and encode the important constraints as fitness functions. For formatting, linting, security: automate them. We should not be arguing about whitespace in 2026.

The radical implication: code review by exception, not by default. There are changes that absolutely warrant another human looking. Fundamental architectural changes. Anything crossing security boundaries. Changes with huge blast radius. Anything the team says they're not confident about. But not every line. Not because agents will review them faster, but because waiting until code review to have important conversations is architecturally backwards.

Rachel's worry about Brian's argument is sharp. He talks about teams accumulating cognitive debt: the software grows while the humans understanding it shrinks. She agrees this is real. She just doesn't think mandatory pull requests defend against it. If agents produce substantially more implementation, teams need to be deliberate about maintaining understanding through collaborative design, pairing, good boundaries, executable architecture, shared operational responsibility.

The framing at the end is perfect: we need engineers to understand systems, not diffs.

Code review was a workaround. It worked when humans could only produce code at a certain speed. That constraint is gone. So the question isn't how to review code faster. The question is why we're waiting until code review to have all the important conversations. Pairing earlier solves more problems. Design sessions solve more problems. Shared responsibility solves more problems. Code review, inherited as ceremony, solved them all at once but badly.

The AI explosion isn't breaking code review. It's exposing that code review was the wrong tool all along.
